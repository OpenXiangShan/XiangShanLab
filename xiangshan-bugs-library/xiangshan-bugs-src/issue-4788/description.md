LLPTW contains 6 entries, meaning it supports a parallelism of 6 and can handle 6 page table walk requests simultaneously. These 6 requests may be different or identical (i.e., located within the 8 PTEs that can be fetched in a single memory access, as 512 / 64 = 8). Therefore, when any entry in LLPTW transitions states, it must check for duplicates among existing entries. If a duplicate is found, a memory access can be avoided by directly copying the result from the existing entry, thus preventing redundant lookups.

According to the design intent, when an entry’s `mem_arb.io.out.fire` signal is asserted, it should compare whether any other entry currently in the `state_hptw_req` or `state_hptw_resp` states has the same VPN. If such an entry exists, the other entry's state should be updated to `state_mem_waiting`, and its HPTW response result should be copied. This logic is already reflected in the code (see https://github.com/OpenXiangShan/XiangShan/blob/1cbe3869e6aabb705ef240e608d13e2917613ff0/src/main/scala/xiangshan/cache/mmu/PageTableWalker.scala#L887).

However, for entries in the `state_hptw_req` state, when the entry sends a request to HPTW, the `hyper_arb1.io.out.fire` signal will be true (see https://github.com/OpenXiangShan/XiangShan/blob/1cbe3869e6aabb705ef240e608d13e2917613ff0/src/main/scala/xiangshan/cache/mmu/PageTableWalker.scala#L928). At this point, the assignment to `state(i)` in https://github.com/OpenXiangShan/XiangShan/blob/1cbe3869e6aabb705ef240e608d13e2917613ff0/src/main/scala/xiangshan/cache/mmu/PageTableWalker.scala#L894 will be overwritten by the assignment in https://github.com/OpenXiangShan/XiangShan/blob/1cbe3869e6aabb705ef240e608d13e2917613ff0/src/main/scala/xiangshan/cache/mmu/PageTableWalker.scala#L931, which is inconsistent with the intended design.

Therefore, this commit introduces a new signal `block_hptw_req(i)`, which indicates that the state of `state(i)` can be directly forwarded to `state_mem_waiting` without sending another redundant request to the HPTW.
