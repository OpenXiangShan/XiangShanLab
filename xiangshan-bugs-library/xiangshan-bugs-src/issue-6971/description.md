### Describe the bug

After entering Debug Mode because of a critical error with `dcsr.CETRIG=1`, clearing CETRIG immediately exposes the sticky critical-error state while the hart is still in Debug Mode. The CPU then fails to retire the clearing instruction and cannot reach the following CSR readback or `DRET`.

The native reproducer first enters Debug through a halt request, sets CETRIG and returns to M-mode. An M-mode `ECALL` with `mnstatus.NMIE=0` and `mstatus.MDT=1` then enters critical-error Debug Mode with `dcsr.cause=7`, `extcause=0`. The Debug handler checks the saved state and executes `CSRRC x0, dcsr, x5` with `x5=0x80000` to clear CETRIG.
                                                                                                                                                                                                
The CSR waveform shows the clear being accepted and CETRIG becoming 0. At that point the critical output becomes 1, but `debugMode` remains 1 for the rest of the observation. No subsequent valid CSR request or DRET request appears. The retirement trace ends immediately before the clearing instruction.

The same ELF was executed twice: once for the initial failure and once with only read-only FST observation enabled. Their raw retirement captures are byte-identical. The platform observer holds critical for 8192 samples and stops the host with exit code 87; that stop is an observation boundary, not a passing testcase result.

### Expected behavior

The architectural basis is the target-recorded **RISC-V Debug Specification 1.0, Ratified, revised 2025-02-21**, section 4.9.1 (`dcsr.cetrig`), together with **Smdbltrp 1.0, Ratified 08/2024**:

- Returning from a critical-error Debug entry restores the critical-error state.
- With CETRIG=1, resuming causes immediate Debug reentry.
- The debugger may resume with CETRIG=0 to allow the platform's critical-error action.

The debugger must therefore be able to clear CETRIG and complete the resume sequence. The observed failure is that the hart remains in Debug and cannot execute DRET. The report does not rely on the critical output's early assertion alone being a violation.

Sources: [official Debug specification](https://docs.riscv.org/reference/debug/index.html) and [fixed Smdbltrp specification source](https://github.com/riscv/riscv-double-trap/blob/639509348415f8d585647353268eb8b53490e499/src/riscv-double-trap.adoc). The retained target PDF is SHA256 `ce2787b25233a6109c9bc767b2bc497798148b721390f72fb9b48ff0ed986fc8`.

### Additional context

At the tested revision, [NewCSR.scala:1516](https://github.com/OpenXiangShan/XiangShan/blob/1fd6f257469ba99a00004595c92a3e5d482e9619/src/main/scala/xiangshan/backend/fu/NewCSR/NewCSR.scala#L1516) exposes the sticky critical latch whenever CETRIG is 0, without excluding Debug Mode:


The signal reaches ROB through [Backend.scala:312](https://github.com/OpenXiangShan/XiangShan/blob/1fd6f257469ba99a00004595c92a3e5d482e9619/src/main/scala/xiangshan/backend/Backend.scala#L312) and [CtrlBlock.scala:801](https://github.com/OpenXiangShan/XiangShan/blob/1fd6f257469ba99a00004595c92a3e5d482e9619/src/main/scala/xiangshan/backend/CtrlBlock.scala#L801). [Rob.scala:769–785](https://github.com/OpenXiangShan/XiangShan/blob/1fd6f257469ba99a00004595c92a3e5d482e9619/src/main/scala/xiangshan/backend/rob/Rob.scala#L769) includes it in `blockCommit`, which disables committing.

This explains the observed sequence: clearing CETRIG in critical Debug exposes the signal before the clear retires, preventing subsequent Debug execution and DRET. The CSR state changes are directly observed; ROB blocking is inferred from the fixed source, because ROB internals are not exposed in this waveform. The five source files were verified against the exact target revision, and the generated NewCSR RTL retains the same critical-output expression.

A fix should preserve the ability to complete Debug execution and DRET after clearing CETRIG, while restoring the platform critical-error behavior on resume. No proposed fix has yet been revalidated on a rebuilt CPU.
