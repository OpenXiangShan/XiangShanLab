# 09-SC设计分析与刷新方案

> 本文档是 SC（`Sc`）的**真实刷新方案**，属于 [01-BPU刷新方案概览](01-BPU刷新方案概览.md) §6.1 占位阶段之后的落地内容：实现时用 §4.6 的真实完成条件替换 `Sc.scala` 中的 `io.resetDone.get := true.B` 恒真占位。
>
> 1. **接口契约**：`contextFlush`/`bpuFlushing`/`resetDone` 由 `BasePredictorIO` 以 `Option.when(HasBpuFlush)` 声明（01 §5.1.3），BPU 顶层已按本事务 `activeFlushMask` 门控后下发（01 §5.3.3）。SC 对应 `scFlushEnable`，因此收到的均为针对自身的有效信号。
> 2. **编译开关**：本文所有刷新端口、SRAM `extraReset`、WriteBuffer 清空、寄存器清零、预测/训练门控、S1 读有效寄存器和 `resetDone` 生成，均遵循 [00-BPU刷新机制编译开关实现方案](00-BPU刷新机制编译开关实现方案.md) §3.1 和 01 §6.2，受 elaboration-time `HasBpuFlush` 统一裁剪。
> 3. **编码规则**：可选端口用 `Option.when(HasBpuFlush)`；端口连线、刷新专用寄存器、`when`/`Mux` 和完成逻辑放入 Scala `if (HasBpuFlush)`；修改既有数据通路时，`else` 必须恢复刷新引入前的原表达式。禁止用 `getOrElse(false.B)` 把可选刷新端口变成常驻硬件后仅依赖综合优化。
> 4. **关闭语义**：`HasBpuFlush=false` 时，SC 刷新专用端口和消费逻辑不参与 elaboration，SC 原有预测、训练、SRAM 与 WriteBuffer 数据通路保持不变；完整裁剪清单见 §4.7。

## 1. SC 的预测流水线

SC 顶层模块为 `Sc`，位于 `src/main/scala/xiangshan/frontend/bpu/sc`。

SC（Statistical Corrector）是 TAGE 后面的统计修正器。它不独立发现分支，而是根据 mBTB/TAGE 已经给出的条件分支结果，计算多个统计表的统计分数之和，并决定是否用 SC 方向覆盖 TAGE 方向。

SC 使用的表包括：`pathTable`、`globalTable`、`bwTable`、`imliTable`、`biasTable`。

### 第一拍：S0 读表

S0 根据 `startPc`、路径历史、全局历史、Backward 历史、IMLI 历史计算各类表的 index，并根据 PC 计算 bank mask。所有预测读请求都以 `s0_fire` 为共同前提；在此基础上，path/imli/bias 分别受各自 enable 控制，globalTable 和 bwTable 还要求 `s0_commonHR.valid`。如果 common history 无效，globalTable/bwTable 不会发读请求，S1 对应响应也会被当作 0 处理。

默认配置：

```text
PathTable:     2 张，每张 128 set
GlobalTable:   2 张，每张 128 set
BackwardTable: 2 张，每张 128 set
ImliTable:     1 张，128 set
BiasTable:     1 张，128 set
每张表 2 bank
```

每个 `ScTable` 内部是单端口 SRAM 加写缓冲。普通 SC 表的 way 数等于 `NumWays`，biasTable 的 way 数是 `BiasTableNumWays = NumWays << BiasUseTageBitWidth`，因为它把 TAGE provider 的 taken/weak 信息也编码进 way 选择。

### 第二拍：S1 计算 percsum

S1 读回各表的 `ScEntry`，并把各表 counter 转成带符号的 percsum。源码中的 `getPercsum(ctr)` 是 `Cat(ctr, 1.U).asSInt`，相当于把 6 bit signed counter 左移 1 位并在最低位补 1，再参与后续求和；不是给不同表乘不同权重。

SC 会分别计算：path percsum、global percsum、backward percsum、imli percsum、bias percsum。

### 第三拍：S2 生成 SC 修正结果

S2 将 S1 提前求和的 path/global/backward/imli percsum 与 bias percsum 相加，得到最终 `totalPercsum`。`totalPercsum >= 0` 得到 SC 自己的 taken/not-taken 方向；是否真正采用 SC 结果，还要同时满足 mBTB 条件分支有效、TAGE provider counter 有效，并根据 TAGE provider counter 置信度选择不同阈值：

- provider counter 饱和强置信：使用 `scThreshold >> 4`
- provider counter 中等置信：使用 `scThreshold >> 5`
- provider counter 弱置信：使用 `scThreshold >> 6`

源码中还定义了 `s2_thresholds = scThreshold >> 3`，但当前 `s2_useScPred` 的判断实际使用的是上面三个 `s2_sumAboveThresholdShift*` 结果。

方向结果 `io.scTakenMask` 和选择信号 `io.scUsed` 在 S2 组合生成；`io.meta` 中的 `scPred`/`tagePred`/`tageCtr`/`tagePredValid`/`useScPred`/`sumAboveThres` 等字段则在 `s2_fire` 时寄存，作为 S3 随预测结果保存的训练 meta。

其中 `scUsed` 表示是否真正使用 SC 修正 TAGE 结果。源码保证 `scUsed` 为真时 TAGE provider 必须有效，否则会触发 `XSError`。

## 2. SC 的训练流水线

SC 训练从 T0 到 T2，共三拍。

### T0：判断是否需要训练并读表

T0 根据训练分支、mBTB meta、SC meta 判断是否需要更新 SC。它先按预测时的 mBTB entry 顺序找到训练分支对应的预测结果槽位 `predIdx`，用该索引读取 SC meta；各表实际更新的 way 则由训练分支 `cfiPosition` 经 `getWayIdx` 另行计算。只有命中 mBTB、是条件分支、且 `tagePredValid(predIdx)` 为真的分支才可能训练 SC。

训练触发条件不是“所有条件分支都训练”。源码里的 `t0_writeValidVec` 还会过滤掉不需要更新的情况：当 SC 已经被使用、SC 方向正确、且 SC 方向与 TAGE 方向相同时，这次训练会被跳过；其他需要纠正或置信不足的情况才会读表更新。

如果至少一个分支需要训练，则向所有相关 `ScTable` 发训练读请求。训练读和预测读共享同一个 single-port SRAM，因此同 bank 冲突时通过 `trainReady` 反压训练。globalTable 和 bwTable 的训练读还要求 `commonHR.valid`，path/imli/bias 不依赖该 valid。

### T1：计算新 counter 和 threshold

T1 根据旧表项和真实方向，计算新的 `ScEntry` counter。只有在 SC 错误或 `sumAboveThres` 为假时才更新对应表项；biasTable 的 way 选择还会使用预测阶段保存的 `scBiasLowerBits`。

同时，T1 会更新顶层 `scThreshold`。对每个满足表项更新条件的分支：

- SC 方向错误时，对该分支实际写入 way 的 threshold 计一次增加；
- SC 方向正确但 `sumAboveThres` 为假时，对该 way 的 threshold 计一次减少。

同一拍内多个 resolved branch 的增减次数会按 way 汇总后取净值；候选结果只有位于 `[MinThreshold, MaxThreshold]` 内时才写入，越界时保留原 threshold。

`scThreshold` 是顶层寄存器状态，不在 SRAM 中。

### T2：生成 way mask 并写入各类 ScTable

T2 寄存 T1 算出的新 entry 及对应的旧 entry，比较两者生成实际发生变化的 way mask，再向各类 `ScTable` 的 `update` 端口发写请求。每个 `ScTable` 内部不会直接写 SRAM，而是先写入 `WriteBuffer`，后续在 SRAM 读端口空闲时写回。

## 3. SC 的整体架构

本节只列 SC 内部需要刷新关注的存储结构，不展开读写请求和 meta 这类接口结构。

默认参数：

```text
CtrWidth = 6
ThresholdWidth = 13
NumBanks = 2
WriteBufferSize = 4
NumWays = NumBtbResultEntries = 8
BiasUseTageBitWidth = 2
BiasTableNumWays = 8 << 2 = 32
所有 SC table 默认 NumSets = 128
```

SC 使用的表：

| 表              | 数量 | 每张表 set 数 | way 数 | history length |
| --------------- | ---: | ------------: | -----: | -------------: |
| `pathTable`   |    2 |           128 |      8 |         8 / 16 |
| `globalTable` |    2 |           128 |      8 |         8 / 16 |
| `bwTable`     |    2 |           128 |      8 |          4 / 8 |
| `imliTable`   |    1 |           128 |      8 |              8 |
| `biasTable`   |    1 |           128 |     32 |              0 |

### 3.1 ScTable SRAM

**ScEntry 的数据结构**

SC 表项没有 valid 位，只有一个有符号统计计数器：

```text
ScEntry (6 bits)
 └── ctr: SignedSaturateCounter(6) — 6 bits 有符号统计 counter
```

**普通 SC 表结构**

普通表包括 `pathTable/globalTable/bwTable/imliTable`，每个 `ScTable` 内部有 2 个 bank，每个 bank 是 128 行、8 way。

```text
普通表每行 = Vec(8, ScEntry) = 8 × 6 bits = 48 bits
```

每个普通表：

```text
2 bank × 128 行 × 8 way × 6 bits
```

**biasTable 结构**

`biasTable` 的 way 数是 `BiasTableNumWays = 32`。相比普通表多出来的 2 bit way 选择来自 TAGE provider 的 weak/taken 信息；代码分别编码为 `providerValid && ctr.isWeak` 和 `providerValid && taken`，provider 无效时两位均为 0。

```text
biasTable 每行 = Vec(32, ScEntry) = 32 × 6 bits = 192 bits
```

每个 biasTable：

```text
2 bank × 128 行 × 32 way × 6 bits
```

注意：biasTable 只增加每行 way 数，不增加 SRAM 行数，所以刷新 SRAM 时深度仍是 128 行。

### 3.2 WriteBuffer

**WriteBuffer 的数据结构**

每个 `ScTable` 的每个 bank 都有一个写缓冲：

```scala
WriteBuffer(
  new ScTableSramWriteReq(numRows, numWays),
  WriteBufferSize,
  numPorts = 1,
  numWays = numWays,
  hasWayMask = true
)
```

写缓冲项为 `ScTableSramWriteReq`。

普通表写缓冲项：

```text
ScTableSramWriteReq (63 bits)
 ├── setIdx:  UInt(7)              — 7 bits  写回 set
 ├── wayMask: Vec(8, Bool)         — 8 bits  写回 way mask
 └── wayData: Vec(8, UInt(6.W))    — 48 bits 写回 counter 数据（`ScEntry` 位模式）
```

biasTable 写缓冲项：

```text
ScTableSramWriteReq (231 bits)
 ├── setIdx:  UInt(7)              — 7 bits   写回 set
 ├── wayMask: Vec(32, Bool)        — 32 bits  写回 way mask
 └── wayData: Vec(32, UInt(6.W))   — 192 bits 写回 counter 数据（`ScEntry` 位模式）
```

每个 bank 的 `WriteBufferSize = 4`，核心状态包括：

```text
entries:      4 项 ScTableSramWriteReq
dirty:        4 bits  — 待写回 SRAM 的标记
shadowValid:  4 bits  — shadow 表项有效标记
```

如果刷新只清 SRAM、不清 WriteBuffer，旧 counter 更新可能在 SRAM 清零后继续写回。

### 3.3 scThreshold

`scThreshold` 是 SC 顶层的阈值寄存器数组：

```scala
private val scThreshold = RegInit(VecInit.tabulate(NumWays)(_ => ThresholdCounter.Init))
```

```text
scThreshold
 ├── 8 项 ThresholdCounter
 └── 每项 13 bits

总宽度 = 8 × 13 = 104 bits
```

它决定 SC percsum 达到多大幅度才允许覆盖 TAGE。该状态由训练历史积累而来，context flush 时应恢复初始值。

## 4. 刷新方案

> 本节对齐 [01-BPU刷新方案概览](01-BPU刷新方案概览.md) 的接口契约。SC 包含需要多拍清零的 **SRAM 状态**（见本文 §3.1）。`BasePredictorIO` 已用 `Option.when(HasBpuFlush)` 声明 `contextFlush`/`bpuFlushing`/`resetDone`。
> **核心规则**：`contextFlush` 负责触发/清除状态；`bpuFlushing` 用于关闭 ScTable 读请求和 WriteBuffer 新入队，并门控训练通路。WriteBuffer 出队/写回保持原有 `valid/ready` 仲裁，不额外使用 `bpuFlushing` 门控。`resetDone` 仅由 SC 本地 SRAM 完成状态生成，不得依赖 `bpuFlushing` 拉低，否则会与 BPU 顶层的聚合 `resetDone` 形成循环等待。
>
> **BPU 顶层到 Sc 的三个握手端口**（01 §5.1.3）：
>
> | 端口                                                                                                                                                                                 | 方向 / 类型                           | 作用                                                 |
> | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :------------------------------------ | :--------------------------------------------------- |
> | `io.contextFlush.get`                                                                                                                                                              | Input /`Option[Bool]`，1-cycle 脉冲 | 触发**清零**状态                               |
> | `io.bpuFlushing.get`                                                                                                                                                               | Input /`Option[Bool]`，电平         | 刷新整窗门控 SRAM 读请求、WriteBuffer 入队和训练通路 |
> | `io.resetDone.get`                                                                                                                                                                 | Output /`Option[Bool]`              | 本预测器**自身清零完成**                       |
> | 与`s0_fire`/`s1_fire`/`s2_fire` 等模块内部控制信号的风格一致，SC 顶层只在一处解包可选 IO；后续门控统一使用模块内部信号，不直接使用 `io.*` 参与 `when`/`Mux`/布尔表达式： |                                       |                                                      |
>
> ```scala
> // Sc.scala：只在此处解包 BasePredictorIO 的刷新输入为模块内部别名。
> private val contextFlush = if (HasBpuFlush) io.contextFlush.get else false.B
> private val bpuFlushing  = if (HasBpuFlush) io.bpuFlushing.get  else false.B
> ```

推荐新增的 SC context flush 按三层处理：

1. **清空表项 / 存储结构**：清所有 ScTable SRAM、WriteBuffer，恢复 `scThreshold` 初始值。
2. **隔离并复位预测残留**：预测 stage fire 保持原逻辑，只关闭实际 SRAM 读；S1 用“实际读请求”的有效位屏蔽 `holdRead` 旧值，模块内部 `contextFlush` 当拍将 S1、S2 与 meta/debug 的所有预测 payload 寄存器恢复为各自规定的初始状态（见 §4.4）。
3. **阻断会修改状态的新数据进入流水线**：预测/训练读请求、训练入口和 WriteBuffer 新入队被 `bpuFlushing` 阻断，覆盖 T 拍至顶层聚合 `resetDone` 置位。WriteBuffer 旧内容则由 `contextFlush` 当拍清空，出队/写回不增加额外窗口门控。

### 4.1 ScTable SRAM 刷新方案

SC 表项没有 valid 位，counter 本身就是预测状态，因此 context flush 需要把所有 `ScEntry.ctr` 清零。ScTable 的修改分为 I/O 接口修改、清空 SRAM 和刷新期间的读写污染三部分。

#### 4.1.1 I/O 接口修改

BPU 顶层 → Sc 的 `contextFlush`/`bpuFlushing`/`resetDone` 接口以及 Sc 内部解包已在 §4.1 之前完成。本节只新增 **Sc → ScTable** 的表级刷新接口：`ScTableIO` **增加 `contextFlush`/`bpuFlushing`** 两个受 `HasBpuFlush` 裁剪的可选输入。

可选输入在 ScTable 内只解包一次为 Scala `val` 别名；后续 `when`/valid/ready 门控不直接使用 `io.contextFlush.get` 或 `io.bpuFlushing.get`。

```scala
// ScTable.scala
class ScTableIO extends ScBundle {
  ...
  // [新增] 表级刷新接口；关闭时结构性消失。
  val contextFlush: Option[Bool] = Option.when(HasBpuFlush)(Input(Bool()))
  val bpuFlushing:  Option[Bool] = Option.when(HasBpuFlush)(Input(Bool()))
}
val io: ScTableIO = IO(new ScTableIO)

// ScTable 解包，后续 SRAM/WriteBuffer 门控使用这两个内部别名。
private val contextFlush = if (HasBpuFlush) io.contextFlush.get else false.B
private val bpuFlushing  = if (HasBpuFlush) io.bpuFlushing.get  else false.B
```

#### 4.1.2 清空 SRAM

当前 SRAM 只有上电 reset（`shouldReset = true`），无运行时 extra reset（[ScTable.scala:53-66](../../../src/main/scala/xiangshan/frontend/bpu/sc/ScTable.scala#L53-L66)）。实现时将 `extraReset` 设为 elaboration-time `HasBpuFlush`，并由模块内部 `contextFlush` 驱动 `extra_reset`。

所有 SC 表和 bank 并行进行 extra reset。默认每个 bank 的 `numRows = 128`，清零时间约为 128 cycles。

```scala
// ScTable.scala

private val sram = Seq.fill(NumBanks)(
  Module(new SRAMTemplate(
    new ScEntry(),
    set = numRows,
    way = numWays,
    singlePort = true,
    shouldReset = true,
    extraReset = HasBpuFlush, // [修改] 关闭时 extra-reset 端口与逻辑均不生成
    holdRead = true,
    ...
  ))
)

// [新增] 触发运行时 SRAM 清零。
if (HasBpuFlush) {
  sram.foreach { bank => bank.extra_reset.get := contextFlush }
}
```

#### 4.1.3 刷新期间的读写污染

ScTable SRAM 自身复位只负责两件事：一是 `extraReset` 触发后由 `SRAMTemplate` 按 `resetSet` 自主逐行写零；二是清零期间以 `resetHold` 拉低读、写请求的 `ready`，使外部请求不能握手。它不会自动清除 SRAM 外部的预测流水线和 WriteBuffer 状态，也不能保证 reset 写模式下的 `io.r.resp.data` 具有合法读响应语义。因此，SC 采用以下四层防护以**防止刷新期间对 SRAM 的读写污染**，四层防护合并后的完整逐拍时序见 §5。

**层面一：清空 ScTable SRAM 和 WriteBuffer。** §4.1.2 用 `extraReset` 清空已写入 SRAM array 的旧 counter；§4.2 在 `contextFlush` 当拍清除 WriteBuffer 中尚未写回、仍可能参与命中/合并的旧更新。

**层面二：阻止 ScTable SRAM 的非法读回进入预测路径。** `SRAMTemplate` 在 reset 清零期间不接受读请求，故此时 SRAM 数据输出不能视为有效响应，具体见 §4.4：

- 预测读和训练读在 ScTable 内使用 `!bpuFlushing` 关闭 SRAM 读请求，避免普通读与 reset 写争用 single-port SRAM。
- Sc 顶层另用“实际读请求”对齐的 valid 隔离 `holdRead = true` 保留的旧数据，无有效响应时强制向后续计算提供全零 `ScEntry`。

**层面三：阻止刷新期间重新写入 WriteBuffer。** Sc 顶层在 §4.5 阻断 T0～T2 训练 valid；ScTable 内部再在 WriteBuffer 入队 valid 上使用 `!bpuFlushing`（§4.2）。两级门控共同保证 WriteBuffer 清空后不会产生新的 counter 更新。

**层面四：出队方向不设门控。** WriteBuffer 到 SRAM 的写回 `valid` 和出队 `ready` 保持 ScTable 现有仲裁表达式，不额外串接 `bpuFlushing`。刷新安全依赖“**触发拍残留写回可覆盖 + 复位反压 + buffer 已清空 + 新入队门控**”共同保证：

- **触发拍残留写回可覆盖**：T 拍 `contextFlush` 拉高时，`SRAMTemplate` 内部 `resetState` 要到时钟沿后才生效，因此当拍组合路径上可能仍有一次旧 WriteBuffer 写入。该写入发生在 SRAM 逐行清零之前，后续 reset 写零会覆盖其写入 set。
- **复位期反压**：T+1 起 `SRAMTemplate` 进入 reset 清零态，拉低写请求 `ready`，并由 reset 地址、零数据和全 way mask 接管 SRAM array。WriteBuffer 出队 `ready` 自然随 SRAM 写端 `ready` 拉低，出队请求不会完成握手。
- **窗口内 buffer 为空**：层面一在 T 拍清除 WriteBuffer 有效状态，层面三拦截窗口内的新入队请求。SRAM 写口恢复时，buffer 中不存在旧待写项，因此不会把已清零的 SRAM 重新写脏。

由此，WriteBuffer 无需等待出队排空，也无需提供 `writeBufferEmpty` 完成接口；**`resetDone` 只等待所有 ScTable SRAM 清零完成**，见 §4.6。

### 4.2 WriteBuffer 刷新方案

SC 训练写先进入 `WriteBuffer` 再写回 SRAM。若只清 SRAM，WriteBuffer 中的旧待写 counter 可能延后写回，其 shadow 状态也可能参与新请求的同 set 命中和合并。本节按 I/O 接口复用、复用现有逻辑清空 WriteBuffer、以及刷新期间的读写污染三部分说明；09 RTL-SPEC 不修改共享 `WriteBuffer` 模块。

#### 4.2.1 I/O 接口修改

WriteBuffer 在 `ScTable` 内按 bank 实例化：**刷新信号直接使用 §4.1.1 中的 ScTable 内部 `contextFlush`，I/O 则复用 03 RTL-SPEC 已定义的 `hasContextFlush` 参数和可选 `io.contextFlush` 输入**。

SC 只需在实例点传入 `HasBpuFlush` 并连接 `contextFlush`。`hasContextFlush=false` 时 `contextFlush` 端口和相关清空逻辑均不生成。WriteBuffer 不需要 `bpuFlushing` 输入，刷新期间的新入队门控放在 ScTable 的 WriteBuffer 输入侧完成。

```scala
// ScTable.scala：复用共享 WriteBuffer 已有的 context-flush 接口。
private val writeBuffer = Seq.tabulate(NumBanks)(bankIdx =>
  Module(new WriteBuffer(
    new ScTableSramWriteReq(numRows, numWays),
    WriteBufferSize,
    numPorts = 1,
    numWays = numWays,
    hasWayMask = true,
    hasContextFlush = HasBpuFlush, // ScTable 实例点启用现有接口
    nameSuffix = s"sc${tableType}${tableIdx}_${bankIdx}"
  ))
)

if (HasBpuFlush) {
  writeBuffer.foreach { buffer => buffer.io.contextFlush.get := contextFlush }
}
```

#### 4.2.2 清空 WriteBuffer

**09 RTL-SPEC 不在 `WriteBuffer.scala` 中新增或修改清空逻辑**，SC 直接复用 03 RTL-SPEC 已实现的 context-flush 语义。WriteBuffer 中与该语义直接相关的状态是 `dirty` 和 `shadowValid`：1）`dirty` 表示该槽仍有待写回 SRAM 的数据；2）`shadowValid` 表示 `entries` 中的 shadow 数据仍可参与同 set 命中和合并。

当前 WriteBuffer 模块内部已经部署上下文切换刷新机制：

- `contextFlush` 有效时，WriteBuffer 在每个 row 的 next-state 计算末尾将全部 `nextDirty` 和 `nextShadowValid` 清零。由于该赋值位于 `io.read.fire` 出队处理以及入队、命中合并处理之后，因此会覆盖这些逻辑对 `nextDirty` 和 `nextShadowValid` 的同拍更新。时钟沿后，`dirty` 和 `shadowValid` 均更新为零：WriteBuffer 不再产生有效出队请求，旧 entry 也不再参与后续命中与合并。
- `entries` 数据和内部 PLRU 状态无需清零：`shadowValid=false` 后残留 entry 不可见，PLRU 只影响后续替换选择，不会使旧数据重新有效。

```scala
// WriteBuffer.scala：03 基线已有逻辑，仅用于说明复用的清空语义。
if (hasContextFlush) {
  when(flush || contextFlush) {
    for (i <- 0 until numEntries) {
      nextDirty(nRows)(i) := false.B
    }
  }
  when(contextFlush) {
    for (i <- 0 until numEntries) {
      nextShadowValid(nRows)(i) := false.B
    }
  }
}
```

#### 4.2.3 刷新期间的读写污染

清空 WriteBuffer 后还需阻止新训练请求重新入队。Sc 顶层在 §4.5 阻断 T0～T2 训练 valid，ScTable 内部再在 WriteBuffer 入队 valid 上使用 `!bpuFlushing`，作为靠近状态修改点的第二层防护。

```scala
// ScTable.scala：[修改] 刷新期间禁止新入队。
writeBuffer.zip(updateBankMask.asBools).foreach {
  case (buffer, bankEnable) =>
    val rawWriteValid = updateValid && bankEnable
    val writeValid = if (HasBpuFlush) rawWriteValid && !bpuFlushing else rawWriteValid

    buffer.io.write.head.valid       := writeValid
    buffer.io.write.head.bits.setIdx := updateIdx
    buffer.io.write.head.bits.wayMask.get := Mux(
      writeValid,
      updateWayMask,
      VecInit.fill(numWays)(false.B)
    )
    buffer.io.write.head.bits.wayData.get := Mux(
      writeValid,
      VecInit(io.update.entryVec.map(_.asUInt)),
      VecInit.fill(numWays)(0.U.asTypeOf(new ScEntry()).asUInt)
    )
}
```

WriteBuffer 出队/写回不额外使用 `bpuFlushing` 门控，保持 ScTable 现有仲裁：

```scala
// ScTable.scala：[不修改] 出队保持原表达式。
bank.io.w.req.valid       := buffer.io.read.head.valid && !bank.io.r.req.valid
buffer.io.read.head.ready := bank.io.w.req.ready && !bank.io.r.req.valid
```

T 拍可能完成的写入会被随后的 SRAM 逐行清零覆盖；T+1 起由 SRAM 写端 `ready` 对出队自然反压；时钟沿后 WriteBuffer 已因 `dirty` 清零而不再提供有效出队请求。因此无需提供 `writeBufferEmpty` 完成接口，`resetDone` 只需等待 ScTable SRAM 清零完成。

### 4.3 scThreshold 刷新方案

`scThreshold` 由训练历史累积而来（[Sc.scala:92](../../../src/main/scala/xiangshan/frontend/bpu/sc/Sc.scala#L92)），是 SC 顶层策略寄存器，不在 SRAM 中。若只清 ScTable SRAM，刷新后仍会保留旧上下文的使用门限。本节按 I/O 接口复用、清空 `scThreshold` 和刷新期间的写污染三部分说明。

#### 4.3.1 I/O 接口复用

`scThreshold` 位于 Sc 顶层，**不需要新增模块间 I/O**。

#### 4.3.2 清空 `scThreshold`

刷新逻辑直接复用 §4.1 之前已解包的 Sc 内部 `contextFlush` 和 `bpuFlushing`：前者恢复门限初始值，后者通过训练流水线门控阻止刷新期间的新更新。

`contextFlush` 当拍将所有 way 的 `scThreshold` 恢复为 `ThresholdCounter.Init`。清零连接放在原有 `when(t1_writeValid)` 之后，利用 Chisel last-connect 保证 context flush 当拍的恢复初始值优先于正常训练写入。

```scala
// Sc.scala：保留原有写入，刷新清零在开关内用 last-connect 覆盖。
when(t1_writeValid) {
  scThreshold := t1_writeThresVec
}
if (HasBpuFlush) {
  when(contextFlush) {
    scThreshold := VecInit.tabulate(NumWays)(_ => ThresholdCounter.Init)
  }
}
```

#### 4.3.3 刷新期间的写污染

`scThreshold` 只有训练写污染，没有 SRAM 读响应类的读污染，其原有写条件为 `t1_writeValid`（[Sc.scala:609](../../../src/main/scala/xiangshan/frontend/bpu/sc/Sc.scala#L609)）。§4.5 在 `t1_fire` 上使用 `!bpuFlushing` 门控，使刷新窗口内的 `t1_writeValid` 为 false，阻止旧训练请求重新改写门限。

因此，`scThreshold` 的正常写条件保持原表达式，不再重复串接 `!bpuFlushing`；`contextFlush` 负责当拍恢复初始值，训练流水线门控负责阻止窗口内的后续写入。

### 4.4 如何防止预测路径污染刷新结果

context flush 触发时，SC 预测流水线中可能仍保存旧上下文的中间结果；同时，`ScTable` 使用 `holdRead = true`，停止读请求后 SRAM 读响应仍会保留上一次读回值。本方案使用以下两种策略隔离这两类旧状态。

**策略一：复位预测流水线中的寄存器**

`contextFlush` 当拍统一复位 Sc 内部所有预测 payload 寄存器，包括 S1、S2 和 `io.meta.*/debug` 的保存寄存器。本方案不再逐项分析旧值是否可由 valid/fire 依赖链间接屏蔽，而是**将全部预测中间状态恢复为各自规定的初始状态**：

- 原本已有明确初值的寄存器复用该初值；
- 原本使用无初值 `RegEnable` 的 payload 寄存器，则需在刷新配置中显式规定初值。

现有 S1/S2 标量和索引已是具名 `RegEnable`，保持原代码，本文不重复列出。需要修改的是目前直接将 `RegEnable` 连到 `VecInit` 或 `io.meta.*` 的字段：先保留真正的底层寄存器引用，再连接组合结果或输出。该修改**不为原本无初值的寄存器增加上电 reset**。

在上述寄存器定义之后集中增加一处刷新块，集中刷新块位于原 `RegEnable` 定义之后，以 last-connect 方式保证 `contextFlush` 优先级高于同拍 `s0_fire/s1_fire/s2_fire`。

策略二的`s1ScReadValid` 在刷新触发拍由`s0ScReadValid=false` 驱动，在时钟沿后恢复为无效状态，无需在集中刷新块中重复赋值。BPU 顶层的`s0_fire/s1_fire/s2_fire` 和各流水级 valid 控制保持原逻辑。ScTable 内的两个读响应 bank-mask 寄存器也在`contextFlush` 时清零，避免刷新后重新选中 SRAM `holdRead` 保留的旧值。

五类响应复用现有 Mux 的全零分支。刷新窗口内，只有上一拍实际发出了预测读请求时，S1 才选择 ScTable 读响应；否则强制向后续 percsum 计算提供全零`ScEntry`。非刷新窗口内`s1ScReadValid=true.B`，因此不影响原有 Mux 选择逻辑。在恢复首拍 T+ka，`s1ScReadValid` 虽然立即为 true，但 ScTable 的`predictReadBankMaskNext` 仍为全零，因此 ScTable 输出仍为全零，不会重新暴露刷新前的`holdRead` 值。

**`scUsed`/`scTakenMask` 的等价无效化**：`s2_useScPred`是由 S2 percsum 和门限组合计算的 Wire，不是需要单独清零的寄存器。刷新时 S2 percsum 寄存器被恢复为零，刷新窗口内 ScTable 响应也持续为零，因此`aboveThreshold(0, threshold)`的严格大于/小于比较结果为 false，使`io.scUsed=false`。`io.scTakenMask`可能因`0 >= 0`而为 true，但 BPU 只在`scUsed=true`时采用该方向，因此该值不会影响最终预测。`io.meta`中的`scPred`/`useScPred`同样以“方向值 + 是否采用”的组合表达这一语义；其寄存器已由策略一在`contextFlush`时钟沿清零。因此无需额外对`scUsed`或`scTakenMask`增加刷新窗口输出门控。

### 4.5 如何防止训练路径污染刷新结果

训练路径会直接修改 SC 状态：T0 发出 ScTable 训练读，T1 根据旧表项计算新 counter 并更新 `scThreshold`，T2 通过 `ScTable.update` 将新表项送入 WriteBuffer。因此同时采用“恢复流水寄存器”和“整窗门控训练更新”两种策略。WriteBuffer 旧待写项由 §4.2 的 `contextFlush` 当拍清除，出队/写回保持原有仲裁。

**策略一：恢复训练流水线 payload 寄存器的初始状态**

`contextFlush` 当拍将 T1/T2 的 payload 寄存器统一恢复为各自规定的初始状态。保留原有 `RegEnable` 定义，不为原本无初值的 payload 增加上电 reset；在所有 T1/T2 payload 寄存器定义之后集中增加刷新块。valid 不在此处重复赋值，由策略二的组合门控当拍阻断，并在刷新窗口内通过 `RegNext` 自然恢复为 false：

```scala
// [新增] contextFlush 时钟沿恢复训练流水 payload。

    t1_pathSetIdx   := 0.U.asTypeOf(t1_pathSetIdx)
    t1_globalSetIdx := 0.U.asTypeOf(t1_globalSetIdx)
    t1_bwSetIdx     := 0.U.asTypeOf(t1_bwSetIdx)
    t1_imliSetIdx   := 0.U.asTypeOf(t1_imliSetIdx)
    t1_biasSetIdx   := 0.U.asTypeOf(t1_biasSetIdx)
    t1_oldBiasLowBits        := 0.U.asTypeOf(t1_oldBiasLowBits)
    t1_branchesScIdxHitVec   := 0.U.asTypeOf(t1_branchesScIdxHitVec)
    t1_branchesScIdxVec      := 0.U.asTypeOf(t1_branchesScIdxVec)
    t1_writeTakenVec         := 0.U.asTypeOf(t1_writeTakenVec)
    t1_writeValidVecReg      := 0.U.asTypeOf(t1_writeValidVecReg)

    t2_bankMask            := 0.U.asTypeOf(t2_bankMask)
    t2_pathSetIdx          := 0.U.asTypeOf(t2_pathSetIdx)
    t2_globalSetIdx        := 0.U.asTypeOf(t2_globalSetIdx)
    t2_bwSetIdx            := 0.U.asTypeOf(t2_bwSetIdx)
    t2_imliSetIdx          := 0.U.asTypeOf(t2_imliSetIdx)
    t2_biasSetIdx          := 0.U.asTypeOf(t2_biasSetIdx)
    t2_commonHR            := 0.U.asTypeOf(t2_commonHR)
    t2_oldPathEntries      := 0.U.asTypeOf(t2_oldPathEntries)
    t2_oldGlobalEntries    := 0.U.asTypeOf(t2_oldGlobalEntries)
    t2_oldBWEntries        := 0.U.asTypeOf(t2_oldBWEntries)
    t2_oldImliEntries      := 0.U.asTypeOf(t2_oldImliEntries)
    t2_oldBiasEntries      := 0.U.asTypeOf(t2_oldBiasEntries)
    t2_writePathEntryVec   := 0.U.asTypeOf(t2_writePathEntryVec)
    t2_writeGlobalEntryVec := 0.U.asTypeOf(t2_writeGlobalEntryVec)
    t2_writeBWEntryVec     := 0.U.asTypeOf(t2_writeBWEntryVec)
    t2_writeBiasEntryVec   := 0.U.asTypeOf(t2_writeBiasEntryVec)
    t2_writeImliEntryVec   := 0.U.asTypeOf(t2_writeImliEntryVec)
  }
}
```

当前无专用初值的 payload 使用对应类型的零值；已有明确初值的寄存器恢复原初值。集中刷新块以 last-connect 方式保证 `contextFlush` 优先级高于同拍训练流水更新。

**策略二：刷新窗口内门控训练请求和状态更新**

训练通路统一使用模块内部 `bpuFlushing` 将阻断窗口覆盖 T 拍至顶层聚合 `resetDone` 置位（01 §5.4）。T0 门控阻止五类 ScTable 训练读请求；T1 门控使 `t1_writeValid=false`，从而阻止 `scThreshold` 更新；T2 门控使所有 `ScTable.update.valid=false`，阻止新表项进入 WriteBuffer。

```scala
// [修改] T0：刷新窗口内不接收新训练，不发出 ScTable 训练读请求。
private val t0_fire = io.stageCtrl.t0_fire && io.enable && (if (HasBpuFlush) !bpuFlushing else true.B)

// [修改] T1：在 RegNext 输出上增加整窗门控。
private val t1_fire = RegNext(t0_fire, false.B) && (if (HasBpuFlush) !bpuFlushing else true.B)

// t1_writeValidVec 使用 t1_fire，因此刷新窗口内 t1_writeValid=false，原 when(t1_writeValid) { scThreshold := t1_writeThresVec } 不会触发。

// [修改] T2：在 RegNext 输出上增加整窗门控，阻断所有 ScTable.update。
private val t2_writeValid = RegNext(t1_writeValid, false.B) && (if (HasBpuFlush) !bpuFlushing else true.B)

// 保留原有 ready 行为。
io.trainReady := !t0_bankConflict
```

`HasBpuFlush=false` 时，`t0_fire/t1_fire/t2_writeValid` 均恢复刷新机制引入前的原表达式，集中刷新块不参与 elaboration。

### 4.6 刷新完成信号 `resetDone`

SC 的 WriteBuffer 在 `contextFlush` 当拍同步清空，且 `bpuFlushing` 在同拍起阻断新入队。触发拍的残留写入会被随后的 SRAM 清零覆盖，复位期出队由 SRAM 写端 `ready` 反压，因此 **`resetDone` 只需等待所有 ScTable SRAM reset 完成**。完成逻辑在实际 `Sc.scala` 中应放在所有 table 实例化之后，避免 Scala 前向引用。

```scala
// Sc.scala
// 只在刷新配置下生成表级连线和 resetDone 逻辑。
if (HasBpuFlush) {
  (pathTable ++ globalTable ++ bwTable ++ Seq(imliTable, biasTable)).foreach { table =>
    table.io.contextFlush.get := contextFlush
    table.io.bpuFlushing.get  := bpuFlushing
  }

  // 复用 Sc 已有的全表 SRAM resetDone 归约。
  // contextFlush 当拍立即拉低；后续由 SRAMTemplate.resetDone 反映逐行清零进度。
  io.resetDone.get := io.sramResetDone && !contextFlush
}
```

`resetDone` 只表示 SC 自身完成；表读请求、WriteBuffer 新入队和训练仍由模块内部 `bpuFlushing` 阻断至 BPU 顶层聚合 `resetDone` 置位。完整逐拍时序见第 5 章。

### 4.7 `HasBpuFlush` 编译裁剪

本节汇总 §4.1～§4.6 的编译裁剪约束。`HasBpuFlush` 是 elaboration-time Scala `Boolean`，不是运行时硬件信号。SC 按照 00 §3.1 和 01 §6.2 的规范，使用“可选 I/O + Scala 条件生成”实现刷新机制；关闭开关时不仅不生成刷新端口，也不生成刷新专用状态和赋值逻辑。

| 位置 | `HasBpuFlush=true` | `HasBpuFlush=false` |
| --- | --- | --- |
| BPU 顶层 → Sc | `BasePredictorIO` 生成`contextFlush`/`bpuFlushing`/`resetDone` | 三个端口均为`None` |
| Sc → ScTable | `ScTableIO` 生成`contextFlush`/`bpuFlushing`，Sc 向所有 ScTable 实例连线 | 表级刷新端口和连线均不生成 |
| 模块内部刷新信号 | Sc 和 ScTable 各自将可选 I/O 仅解包一次为`contextFlush`/`bpuFlushing` | 别名为`false.B`，仅用于统一类型；受 Scala `if` 保护的消费逻辑不生成 |
| ScTable SRAM | `SRAMTemplate(extraReset=true)`，`contextFlush` 连接`extra_reset` | `extraReset=false`，不生成运行时 reset 端口及扫描清零逻辑 |
| WriteBuffer | SC 实例传入`hasContextFlush=true`，复用 03 的`dirty`/`shadowValid` 清空逻辑；新入队受`bpuFlushing` 门控 | `hasContextFlush=false`，保持原 WriteBuffer 结构和入队表达式；两种配置的出队/写回逻辑均不变 |
| `scThreshold` | 生成`contextFlush` 高优先级恢复`ThresholdCounter.Init` 的赋值 | 不生成刷新赋值，仅保留原更新逻辑 |
| 预测通路状态 | 生成`contextFlush` 恢复 S1/S2/meta/debug payload 初始状态的赋值，并清零 ScTable 的`predictReadBankMaskNext`/`trainReadBankMaskNext` | 刷新恢复赋值不参与 elaboration，保留原寄存器结构和更新方式 |
| 预测读通路 | 生成`s0ScReadValid` 和包含`RegNext` 的`s1ScReadValid`；分别门控五类 SRAM 读请求和响应 Mux | `s0ScReadValid=s0_fire`、`s1ScReadValid=true.B`；不生成额外对齐寄存器，读请求和响应选择恢复原行为 |
| 训练流水 | 生成 T1/T2 payload 的`contextFlush` 初始状态赋值；T0～T2 valid 在整个`bpuFlushing` 窗口受门控 | 不生成 payload 刷新赋值；内联 Scala `if` 返回`true.B`，T0～T2 恢复原表达式 |
| SC 完成信号 | 生成`io.resetDone.get := io.sramResetDone && !contextFlush`，直接复用 Sc 已有的全表 SRAM 完成归约 | `resetDone` 端口和赋值均不生成；不影响已有`io.sramResetDone` |

实现时必须遵守以下规则：

1. 所有可选 I/O 使用`Option.when(HasBpuFlush)`。Sc 和 ScTable 内部各自只解包一次，定义为`contextFlush`/`bpuFlushing` Scala `val` 别名。
2. 后续`when`/`Mux`/valid/ready 门控只使用模块内部别名，不直接使用`io.contextFlush.get` 或`io.bpuFlushing.get`。仅在可选端口的解包和连线处使用`.get`。
3. SRAM 完成状态不新增中间 Vec、归约寄存器或本地状态；`resetDone` 必须直接复用已有`io.sramResetDone`，并在`contextFlush` 当拍强制为 false。
4. 仅属于刷新机制的端口连线和集中恢复`when` 必须放在 Scala `if (HasBpuFlush)` 中。对既有数据通路增加的门控，可使用`if (HasBpuFlush) 刷新表达式 else 原表达式`，也可按 §4.5 使用`&& (if (HasBpuFlush) !bpuFlushing else true.B)`；两种写法都必须保证关闭开关时恢复原功能表达式。
5. 禁止通过`getOrElse(false.B)` 解包可选 I/O；统一使用`if (HasBpuFlush) io.<port>.get else false.B` 定义模块内部别名。
6. 共享`WriteBuffer` 的`hasContextFlush` 仍是实例级 Scala 开关。SC 实例必须传入`HasBpuFlush`，不得写死为`true`；`bpuFlushing` 只门控 ScTable 的新入队，不连接 WriteBuffer I/O，也不改动其出队/写回仲裁。
7. 预测读响应屏蔽保持 §4.4 已确认的表达式：`s1ScReadValid = !bpuFlushing || RegNext(s0ScReadValid, false.B)`。ScTable 的两个读响应 bank-mask 寄存器在`contextFlush` 时清零，用于屏蔽恢复首拍的旧`holdRead`。

验收时必须分别 elaboration `HasBpuFlush=true` 和`HasBpuFlush=false` 两种配置，两者均不得出现`None.get`、未连接端口或 FIRRTL 错误。关闭配置的生成 RTL 中不得出现 SC context-flush 可选端口、SRAM `extra_reset`、`s1ScReadValid` 的额外`RegNext`、`resetDone` 刷新赋值、payload 集中恢复赋值，以及读请求/读响应/WriteBuffer 入队/训练的刷新门控；SC 正常预测和训练行为应与未引入刷新机制的基线一致。

最终实现仅修改`Sc.scala` 和`ScTable.scala`；共享`WriteBuffer` 直接复用 03 RTL-SPEC 已有的 context-flush 机制，不修改`WriteBuffer.scala`、`Replacement.scala` 和`Bpu.scala`。

## 5. 刷新过程中的 SC 逐拍时序

逐拍时序（默认配置：2 张 path 表 + 2 张 global 表 + 2 张 backward 表 + 1 张 imli 表 + 1 张 bias 表，共 8 个 ScTable；每表 2 个 bank，因此共 16 个`SRAMTemplate` 并行清零。每个 SRAM 均为 128 set；普通表 SRAM 为 8 way，bias 表 SRAM 为 32 way，同一 SRAM 的所有 way 在同拍写零）：

- **T 拍，触发与组合阻断**：`contextFlush` 和`bpuFlushing` 拉高。`resetDone = io.sramResetDone && !contextFlush` 由`!contextFlush` 组合拉低，屏蔽本拍可能仍为高的`io.sramResetDone` 旧值。`s0ScReadValid=false`，因此五类 ScTable 不再接收新的预测读请求；若 T-1 拍实际发出过预测读，`s1ScReadValid` 仍可通过`RegNext(s0ScReadValid, false.B)` 放行与之对齐的 T 拍响应。`t0_fire`、`t1_fire` 和`t2_writeValid` 全部为 false，不再发出训练读，不更新`scThreshold`，也不向 ScTable 提交 update。WriteBuffer 新入队同样被关闭。由于 SRAM 的`resetState` 尚未置位，本拍组合路径上至多仍可能完成一次旧 WriteBuffer 写回，该写入会被随后的 SRAM 清零覆盖。

- **T 拍时钟沿，刷新状态生效**：16 个 SRAM 的`extraReset` 使其`resetState` 进入清零状态。16 个 WriteBuffer 复用现有`contextFlush` 逻辑，将`dirty` 和`shadowValid` 全部清零。每个 ScTable 的`predictReadBankMaskNext` 和`trainReadBankMaskNext` 同时清零，使 SRAM `holdRead` 保留的旧数据失去可见的 bank 选择状态。同一时钟沿将`scThreshold` 恢复为`ThresholdCounter.Init`，并将 S1/S2/meta/debug 预测 payload 以及 T1/T2 训练 payload 恢复为各自规定的初始状态。训练 valid 不额外显式清零；`t1_fire` 和`t2_writeValid` 内部的`RegNext` 由前级 false valid 自然装入 0。

- **T+1 拍，并行清零开始**：16 个 SRAM 同时向 set 0 的所有 way 写零，`io.sramResetDone=false`，`resetDone=false`。由于 T 拍`s0ScReadValid=false`，本拍`s1ScReadValid=false`，五类预测响应统一为全零`ScEntry`。预测`s0_fire/s1_fire/s2_fire` 保持原有逻辑，因此预测 payload 寄存器仍可按原`RegEnable` 条件继续推进，但不会使用旧的 ScTable 读响应。训练通路和 WriteBuffer 新入队继续阻断。

- **T+2 拍**：16 个 SRAM 同时清零 set 1。预测读请求仍为 false，五类预测响应仍为全零；`t0_fire/t1_fire/t2_writeValid` 和 WriteBuffer 新入队仍然被`bpuFlushing` 阻断。

- **T+2～T+128 拍，清零窗口**：16 个 SRAM 按相同的 set 索引并行扫描；T+2 清 set 1，之后每拍递增 1，T+128 清 set 127。整个窗口内`io.sramResetDone=false`，预测读、训练读、`scThreshold` 更新、ScTable update 和 WriteBuffer 新入队均保持阻断；预测流水 stage fire 本身不停顿，ScTable 响应持续强制为零。

- **T+129 拍，SC 本地完成**：所有 SRAM 的`resetState` 已在 T+128 时钟沿退出，`io.sramResetDone=true`，因此 SC 上报的`resetDone=true`。此时`resetDone` 只表示 SC 本地清零完成；若 BPU 仍在等待其他预测器，`bpuFlushing` 继续为 true，SC 的预测读、训练和 WriteBuffer 新入队仍不恢复。

- **T+129～T+ka-1 拍，等待 BPU 聚合（仅当`ka > 129`）**：`io.sramResetDone` 和`resetDone` 保持为 true，SC 等待 BPU 顶层聚合 `resetDone` 置位。`bpuFlushing` 仍使 SC 保持读请求、训练和新入队阻断。若 SC 是最慢完成的预测器，该等待区间可为空。

- **T+ka 拍，BPU 聚合完成**：`bpuFlushing` 首次拉低。`s0ScReadValid` 恢复为`s0_fire`，本拍可向 ScTable 发出首笔刷新后预测读；`t0_fire` 也可恢复并发出首笔训练读。`s1ScReadValid` 中的`!bpuFlushing` 虽然在本拍立即为 true，但 ScTable 的`predictReadBankMaskNext` 仍为全零，因此预测响应保持为零，不会选中 SRAM `holdRead` 保留的刷新前旧值。T+ka 时钟沿捕获首笔新请求的 bank mask。

- **T+ka+1 拍起，新上下文恢复**：若 T+ka 拍发出了预测读，其对应的新 SRAM 响应在本拍到达，并与 T+ka 时钟沿捕获的新 bank mask 对齐，预测读通路恢复正常行为。若 T+ka 拍接收了有效训练，该事务最早在 T+ka+1 进入 T1，并在 T+ka+2 通过 T2 向 ScTable 提交 update，由对应 WriteBuffer 接收首笔刷新后更新。
