# csr_ooo_read_write Reproduction Guide

This directory is used to observe three different behaviors of CSR instructions in the XiangShan out-of-order core:

| Marker | Instruction | PC | Expected Behavior |
|---|---|---|---|
| (A) | `csrr t3, mscratch` | `0x8000000c` | `mscratch` (0x340) is not on the `CSROoORead` list, so **out-of-order read is allowed**, `waitForward=0` |
| (B) | `addi t4, x0, 0x444` | `0x80000010` | A younger integer instruction with no dependency on (A); **it can execute/write back past (A)** |
| (C) | `csrr t5, mstatus` | `0x80000014` | `mstatus` (0x300) is on the `waitForward` list, so **it must wait for the ROB to drain** before dispatch |
| (D) | `csrw mscratch, t0` | `0x80000018` | CSR write; decode sets `noSpecExec=1`; **always serialized** |
| (E) | `csrw mscratch, t1` | `0x8000001c` | Same as above, and must wait for (D) to commit and leave the ROB |

The program finally jumps in place at `0x80000020`, waiting for the simulation `-C` limit.

## Verify the Disassembly

```bash
cat csr_ooo_read_write.txt
```

Expected output:

```
80000000: 11100293    li    t0,273        # 0x111
80000004: 22200313    li    t1,546        # 0x222
80000008: 33300393    li    t2,819        # 0x333
8000000c: 34002e73    csrr  t3,mscratch   # (A) csr 0x340
80000010: 44400e93    li    t4,1092       # (B) 0x444
80000014: 30002f73    csrr  t5,mstatus    # (C) csr 0x300
80000018: 34029073    csrw  mscratch,t0   # (D)
8000001c: 34031073    csrw  mscratch,t1   # (E)
80000020: a001        j     80000020      # c.j compressed instruction
80000022: 0001        nop                 # alignment padding
```

Notes:

- The immediate of `addi t0,x0,0x111` fits in 12 bits, so `li` expands to a single `addi`;
- `csrr rd, csr` is a pseudo-instruction for `csrrs rd, csr, x0`, and `csrw csr, rs` is a pseudo-instruction for `csrrw x0, csr, rs`;
- `j 1b` is compressed by the assembler into a 2-byte `c.j`, followed by a `c.nop` for alignment; if a 4-byte `j` is desired, add `.option norvc` at the beginning of the asm block;
- The program does not initialize `mscratch`, so its reset value is not guaranteed. In this dump, (A) actually reads `0xc4a64dd286bb263f`
  (see `csrMod.io_out_bits_rData`); do not assume it is 0, and do not rely on this value in the program.

Rules of `vcd_dump.py`:

- Arguments are `<vcd> <start cycle> <end cycle> [signal name substrings...]`, matched against **substrings of the full hierarchical path**;
- **Only non-zero values are printed**: if a signal is not printed for a cycle, it is usually 0;
- Output names are the last 3 path segments; when names collide, pass a longer path in the arguments to disambiguate;
- VCD stores binary values, so **you cannot grep for `0x8000000c`**; use the script to parse them.

### Reading This Program Step by Step

1. **Decode (cycle 4159)**
   - `decode.decoders_0..5.io_deq_decodedInst_pc` = `0x80000000/04/08/0c/10/14`;
   - At this point, `_waitForward` and `_blockBackward` of all CSR instructions are **1** (the original decode attributes),
     including (A) `mscratch` and (C) `mstatus`.
2. **Rename clears the attributes (look at the ROB enqueue port, always together with `_valid`)**
   - At cycle 4162, `rob.io_enq_req_3_valid=1`, `_bits_instr=0x34002e73`, while
     `_bits_waitForward` = **0** and `_blockBackward` = **0**: (A) `mscratch` is not on
     the `CSROoORead` list, so rename cleared its serialization attributes (the script prints only non-zero values, so this line
     is not visible in the `vcd_dump.py` output; in Surfer you can see directly that it is 0);
   - (C) is blocked by waitForward at 4161 and does not enqueue with the group, so **only at cycle 4172** do you see
     `rob.io_enq_req_5_valid=1`, `_bits_instr=0x30002f73`, `_bits_waitForward` = **1**;
     although lane5's waitForward at cycle 4162 is also 1, that is a leftover value from the previous cycle and is meaningless when `valid=0`;
   - The next group's (D)(E) enqueue at cycles 4181/4190 with `waitForward=1`, `blockBackward=1` (CSR writes are always serialized).
3. **Dispatch (from cycle 4161)**
   - 4161: `firedVec_0..4=1` (lanes 0–4 issue), `firedVec_5=0`, `blockedByWaitForward_5=1`:
     (C) is blocked by its own waitForward; older lanes in the same batch must also enter the ROB, so even with
     `io_enqRob_isEmpty=1` it is not allowed through;
   - 4171: the ROB drains, `firedVec_5=1`, and only then does (C) issue;
   - 4172–4179: `blockedByWaitForward_0/1=1` (the valid lanes are D/E); D/E wait for (C) to commit and the ROB to drain again;
   - 4180: `firedVec_0=1`, D issues; 4189: `firedVec_1=1`, E issues.
4. **ROB enqueue and compression (cycle 4162)**
   - At cycle 4162, `rob.io_enq_req_0..4_valid=1`, but `_bits_firstUop` = `1,0,0,1,1`:
     the three consecutive ALU instructions `addi t0/t1/t2` are **compressed into the same ROB entry** by `CompressUnit`
     (`canRobCompress=1` at decode), and the entry records t0; A and t4 each occupy one entry;
   - At cycle 4163, `rob.robBanks_6_0/7_0/0_1_valid=1`, corresponding to entry addresses 6/7/8,
     with `_debug_instr` being `0x11100293`(t0), `0x34002e73`(A), `0x44400e93`(t4) respectively.
5. **CSR FU (reads of A and C)**
   - (A): at cycle 4165, `exus_7.in1ToN.io_in_valid=1`, `csrMod.io_in_bits_op=2` (CSRRS);
     at cycle 4166, `csrMod.io_out_valid=1`, `io_out_bits_rData=0xc4a64dd286bb263f` (the old mscratch value);
   - (C): enters at cycle 4175, and at cycle 4176 `io_out_bits_rData=0xa00000000` (the mstatus value in this dump;
     do not assume it is the reset value); this contrasts with the out-of-order read of mscratch.
6. **CSR writes (D/E)**
   - D enters the FU at cycle 4184 with `io_in_bits_src=0x111`, `op=1` (CSRRW);
     at cycle 4185, `mscratch.w_wen=1`, writing 0x111;
   - E enters the FU at cycle 4193, and at cycle 4194 `mscratch.w_wen=1`, writing 0x222;
     in that cycle `io_out_bits_rData=0x111`, exactly the value D just wrote, showing the two writes are strictly ordered.
7. **Commit (in program order)**
   - Cycles where `commitValid_0_0=1`: 4167 (the `0x11100293` t0 group; t1/t2 retire with it),
     4168 (`0x34002e73` A), 4169 (`0x44400e93` t4), 4178 (`0x30002f73` C),
     4187 (`0x34029073` D), 4196 (`0x34031073` E);
   - (B) t4 can execute earlier than (A), but **its commit is definitely after A**; this dump's debug timestamps
     (`rob.debug_microOp_debugReg_8/7_debugInfo_writebackTime`) also show that t4 writes back earlier than A.

## Common Pitfalls

1. **Data must be ANDed with valid**: `io_commits_info_0_debug_instr` retains its old value on cycles with no commit,
   and a ROB bank's `_debug_instr` is not cleared after `_valid=0`; the same applies to `rob.io_enq_req_*_bits_*`.
   For example, lane5's `waitForward` is already 1 before (C) enqueues, but that is only a leftover value.
2. **t1/t2 having no separate commit record is not a bug**: consecutive `addi` instructions are compressed into t0's ROB entry by `CompressUnit`
   (`canRobCompress`). Check `_bits_firstUop` (lanes 0–2 are 1,0,0) and `_debug_instr` to confirm.
3. **The 0 in `commitValid_0_0` does not mean "ROB entry 0"**: `io.commits.commitValid` is a rotated/compressed
   commit vector; bit0 indicates the oldest committed entry in this cycle; this dump commits 1 entry per cycle.
4. **Decode's `waitForward` is not the final value**: all CSRs are 1 at decode; only rename clears them to 0 according to
   the `CSROoORead` lists. To see the final attributes, use `rob.io_enq_req_*_bits_waitForward`.
5. **mscratch's initial value is not 0**: in this dump, (A) reads `0xc4a64dd286bb263f`; do not assume the reset value is 0,
   and do not rely on it in the program.
6. **VCD values are binary**: use `vcd_dump.py`; do not `grep 0x...`.
7. **Signal visibility changes with the build**: after changing the emu, search by name first, and look for an equivalent signal if not found; the table above is the set actually verified in this dump.
8. The first ~4000 cycles are BootROM/boot code; just look at the window after `-b 4000`.
