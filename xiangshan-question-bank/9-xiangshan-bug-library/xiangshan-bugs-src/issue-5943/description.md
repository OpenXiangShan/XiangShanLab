### Describe the bug

There seems to be a bug in vector strided store exception handling on `kunminghu-v2`.

**Bug Description**

The failing instruction is:

```asm
vsse16.v v20, (s3), t4
```
The relevant state at the fault point is:
```
s3 = 0x19
t4 = 0x1
vl = 25
```
So the store addresses generated by vsse16.v are:
```
element 0: 0x19
element 1: 0x1a
...
element 24: 0x31
```
The reference model reports a store access fault and sets:
```
mtval = 0x19
```
However, XiangShan reports:

```
mtval = 0x31
```
while the trap is still taken on the same `vsse16.v`.

This suggests that the recorded fault address is being overwritten by a later vector element, instead of preserving the earliest faulting address.

A likely cause is in the vector store exception merge path. In VMergeBuffer.scala, the merged exception address is updated with:

```

val vaddr = selVaddr + addrOffset
...
entry.vaddr := vaddr
```
This looks like it may allow a later faulting element in the same vector store to overwrite the earlier one.
