### Describe the bug

This bug also exists in the kunminghu-v3 branch.

`AtomicsUnit` stores exceptions in a persistent register (`AtomicsUnit.scala:100`):

```scala
val exceptionVec = RegInit(0.U.asTypeOf(ExceptionVec()))
```

The `hardwareError` bit is updated only after a DCache response (`AtomicsUnit.scala:390-395`):

```scala
val canTriggerCacheError =
  dcache_resp_tl_error.asUInt.orR && io.csrCtrl.cache_error_enable

exceptionVec(hardwareError) :=
  canTriggerCacheError &&
  dcache_resp_tl_error.tl_corrupt &&
  !dcache_resp_tl_error.tl_denied
```

However, `resetFSM()` does not clear `exceptionVec` (`AtomicsUnit.scala:424-431`):

```scala
def resetFSM(): Unit = {
  state := s_invalid
  out_valid := false.B
  data_valid := false.B
  stdCnt := 0.U
  pdest1Valid := false.B
  pdest2Valid := false.B
}
```

Accepting a new atomic operation also does not initialize the exception vector (`AtomicsUnit.scala:138-145`):

```scala
when (state === s_invalid) {
  when (io.in.fire) {
    uop := io.in.bits.uop
    rs1 := io.in.bits.src_rs1
    state := s_tlb_and_flush_sbuffer_req
    have_sent_first_tlb_req := false.B
  }
}
```

Bug sequence

1. Atomic operation A receives a DCache response with `tl_corrupt=1` and `tl_denied=0`.
2. `exceptionVec(hardwareError)` is set.
3. Operation A writes back and calls `resetFSM()`, but `hardwareError` remains set.
4. A later atomic operation B exits before reaching `s_cache_resp_latch`.
5. These paths update their own exception bits but do not update `hardwareError`.

The TLB path overwrites several exception bits, but not `hardwareError` (`AtomicsUnit.scala:255-265`):

```scala
exceptionVec(loadAddrMisaligned)  := ...
exceptionVec(storeAddrMisaligned) := ...
exceptionVec(storePageFault)      := ...
exceptionVec(loadPageFault)       := ...
exceptionVec(storeAccessFault)    := ...
exceptionVec(loadAccessFault)     := ...
exceptionVec(storeGuestPageFault) := ...
exceptionVec(loadGuestPageFault)  := ...
exceptionVec(breakPoint)          := ...
```

The PMP/PMA path only updates access-fault bits (`AtomicsUnit.scala:303-306`):

```scala
exceptionVec(loadAccessFault) := exceptionVec(loadAccessFault) || ...
exceptionVec(storeAccessFault) := exceptionVec(storeAccessFault) || ...
```

The complete vector, including the stale bit, is then written back (`AtomicsUnit.scala:485-486`):

```scala
io.out.bits.uop.exceptionVec := exceptionVec
```

Consequently, operation B may produce an exception vector such as:

```text
storeAccessFault = 1
hardwareError    = 1  // stale from operation A
```

Impact:
An atomic operation can carry an exception bit generated by an earlier operation.

The ROB treats any set exception bit as an exception (`src/main/scala/xiangshan/backend/rob/Rob.scala:1227-1229`):

```scala
exc_wb.bits.hasException := wb.bits.exceptionVec.get.asUInt.orR
```

Additionally, `MouCfg.exceptionOut` includes `hardwareError` (`src/main/scala/xiangshan/backend/fu/FuConfig.scala:513`):

```scala
exceptionOut = (LduCfg.exceptionOut ++ StaCfg.exceptionOut ++ StdCfg.exceptionOut).distinct
```

### Expected behavior

Every accepted atomic operation should start with an exception vector that does not contain state from a previous operation.
