# Legacy-Issues → Requirements Sub-Skill（上一代遗留问题 → 下一代需求）

> **Source**: Generalized from V(n)→V(n+1) generation-transition
> requirement practice (2026-08). Sanitized for public use: no internal
> names, product IDs, task numbers, or corpus anchors — all concrete
> legacy-issue materials are user-supplied at invocation time (see §1
> input contract).

## When to Use（用途与触发条件）

Use this skill when the user asks you to:

- 编制或修订下一代（V(n+1)）需求文档，且用户提供了上一代（V(n)）遗留问题
  材料（风险登记册 / gap 矩阵 / 评审未闭环项 / 反馈记录 / 交付文档评估）。
- 把上一代产品风险、交付缺口、评审遗留项系统性转化为下一代需求候选。
- 审计"下一代需求里哪些来自上一代遗留"，或反向审计"上一代遗留问题在
  下一代需求中是否均有归宿（转化 / 显式不转化）"。

**Trigger phrases**: "遗留问题", "上一代问题转需求", "V(n) 风险转 V(n+1) 需求",
"legacy issues", "previous-version carryover", "V(n)→V(n+1) delta 输入",
"遗留问题收割", "风险登记册转需求".

**Boundary（与兄弟 sub-skill 的分工）**:

- **本 skill 管上游输入**：代际遗留问题 → 需求候选（generation direction）。
- **gap-analysis** 管单 feature 规范差距深挖（外部 spec vs 内部实现，F{N} doc）。
- **requirement-analysis** 管需求矩阵构建与查询；本 skill 的输出是其
  Phase 1（Ingest & Normalize）输入基线的一部分。

## §1 输入契约：用户提供的遗留问题材料（五源类型学）

**本 skill 不内置任何遗留问题语料。** 调用时用户必须提供材料；以下五源
类型学是材料类型的检查清单，不是库内实例索引。

| # | 材料类型 | 识别特征 | 用户须提供的最小字段 |
|---|---------|---------|---------------------|
| 1 | **产品风险登记册**（上一代交付风险评估） | 风险条目字段：问题/影响/风险级别/来源依据/See（调研笔记锚）；分级 高/中/低 + **双口径**（产品定级 vs 调研评级并注）；状态口径：新增/改级/状态更新/交叉引用；ID 体系：需求号 + 缺陷 ID + 策略项 + 产品优先级（P 级）；常配"无法解决中高风险总表" | 风险条目（含问题/影响/级别）；定级口径（单/双口径）；条目 ID 或行号锚 |
| 2 | **Gap 矩阵**（上一代能力/特性差距） | 现状/要求/Gap/处置/来源 五列结构；处置列直接给下一代动作；每行来源含口述/引言行号锚（逐字）；对标口径降级要显式（对标源不可达 → "观察点"口径） | 五列结构各行（或等效）；行级来源锚；处置列（如已有） |
| 3 | **评审未闭环项** | 评审纪要行号锚；状态"未开始/进行中/带风险交付"；长期未回归项常按缺陷权重成组 | 条目文本 + 闭环状态 + 纪要锚（纪要文件 + 行号/条目号） |
| 4 | **反馈记录**（口述/书面） | 逐字口述记录（材料内定位锚，载体常为工作日志——见 §1.1）+ 优先级编号（如有）；方法论口述（如需求→技术规范转化原则） | 逐字记录文本 + 记录锚 + 优先级（如有） |
| 5 | **交付文档体系差距** | 以下一代需求文档章节为锚的差距行（分类维度 × 现状/要求/Gap）；"需求侧锚点"列直接映射下一代需求编号；区分内部底稿（批评性）与对外口径（roadmap 表述）两件套 | 差距行（分类 × 现状/要求/Gap）；需求侧锚点（下一代编号，如已分配）；内外件区分标注 |

**来源标注要求（HARD）**：

- 每条材料必须可回溯，定位一律采用**材料内定位口径**（以材料自身结构为
  准）：行号 / 条目号 / 章节锚 / 纪要条目 / 日志条目（§1.1），至少其一；
  不使用仓库路径式定位。
- 材料中的 ID 体系（需求号/缺陷号/策略项号）以**用户材料为准**，skill 不
  预设任何编号体系。
- **采集前提**：先按五源逐一盘点用户材料是否覆盖；某源无材料也显式记录
  （"源 N：无材料"），避免把"没提供"静默当作"没有"。

### §1.1 工作日志作为反馈材料载体（单列）

口述/书面反馈最常落的载体是**工作日志**（周志/日报/会议日志）。作为一类
用户提供材料单列约定：

- **定位口径**：日志日期 + 条目号/行号（如"某日日志，第 N 条/第 N 行"），
  日志文件由用户提供；skill 不预设日志的文件命名、存放位置或仓库路径。
- **采集要求**：口述逐字保留（改写即失真）；优先级编号（如有）随条目走；
  记录人/场合可作为口径元信息一并保留。
- **多载体同源**：同一反馈若同时存在于工作日志与正式文档，取权威文档口径
  为主、日志为备注（Source Tag 至少 [UNVERIFIED]，两源互证可升
  [T2-CROSS-CHECKED]，见 §2.5）。

## §2 管线（Pipeline）

```
采集 Harvest ──► 归一 Normalize ──► 可需求化筛选 Triage ──► 需求候选生成 Generate ──► 衔接 Handoff
 (多源收割,      (统一字段:         (三问预判,              (条目模板:               (喂给 requirement-
  保来源锚)       问题/影响/闭环      不转的显式              来源链/必要性/            analysis 的 CSV 纪律:
                  状态/代际归属)      留档)                   验收口径/优先级)          Source Tag 等)
```

### 2.1 采集（Harvest）

1. **多源收割**：对 §1 五源（用户提供的材料）逐一收割，不预设价值——风险
   定级可变（如缓存一致性风险从"低"改"中"），低风险项采集阶段不丢。
2. **保来源锚**：每条问题必须记材料内定位锚（行号 / 条目号 / 章节锚 /
   日志条目，以用户材料自身结构为准，见 §1.1）。口述类以工作日志中的
   逐字记录条目为锚。
3. **双口径保全**：定级冲突时两个口径都收（产品定级 vs 调研评级），不取单一
   覆盖（模式示例：某安全特性——产品"低"（主口径）｜调研"高"（备注口径））。

### 2.2 归一（Normalize）

每条遗留问题统一为以下字段：

| 字段 | 说明 | 模式级取值示例 |
|------|------|----------------|
| 问题陈述 | 一句话、可验收语境 | "调测工作主要针对硅前场景，设计文档未明确硅前/硅后" |
| 影响面 | 客户/生态/合规/性能 | "落地后无硬件调试手段，偏离性能目标" |
| 闭环状态（上一代末态） | 未闭环 / 软件规避 / waive / 带风险交付 / 口径缺（做了工作但未明确） | "口径缺"；"带风险交付（若干已识别缺陷以风险方式交付）" |
| 来源 | 用户材料锚（材料内行号/条目号）+ 该材料中的问题 ID | 材料内定位锚；材料内 ID（以用户体系为准） |
| 代际归属 | V(n) 遗留 / V(n) 未明确 / V(n) 缺失（从零构建） | "V(n) 未明确"；"V(n) 缺失（需从零构建的能力）" |
| 定级 | 含双口径（若冲突） | 产品 低｜调研 高 |

### 2.3 可需求化筛选（Requirementability Triage — 三问预判）

**并非每条遗留问题都应转为需求。** 三问预判（生成侧模型；与需求核查侧的
"三问核查"同名不同向——见本节末边界注）：

- **Q1 必要性**：该问题是否指向下一代必须解决的客户/合规/生态缺口？
  （例：RVA23 必选扩展缺失 → 合规缺口，必转；纯内部打磨项通常不转。）
- **Q2 边界**：能否界定为**产品需求**而非纯研发任务单/缺陷回归？
  （研发内部事务不进需求文档。）
- **Q3 可验收性**：能否写出验收口径（数字/场景/判据）？
  （例：预取提前量实测 120-140ns vs 立项预期 100ns → 可写数字口径。）

**不转的项必须显式留档**（not-converted register），注明三问中哪问未过与
理由。**禁止静默丢弃**。

> **方向边界注**：核查侧三问（Q1 必要的 gap 分析是否做了 / Q2 gap 分析与
> 需求来源是否一致 / Q3 gap 分析与需求描述是否一致）核查的是**已写好的
> 需求文档**；本节三问预判的是**待编制的候选**。同名不同向，勿混用。

### 2.4 需求候选生成（Candidate Generation）

通过三问的条目按以下模板生成候选：

| 字段 | 说明 |
|------|------|
| 需求陈述 | 一句话（产品语言，非实现语言） |
| 来源链 | 遗留问题 → 需求：用户材料锚（材料内行号/条目号/日志条目）+ 上一代 ID（以用户材料 ID 体系为准） |
| 必要性论证 | Q1 结论 + 影响面（客户/生态/合规） |
| 验收口径 | Q3 结论：数字 / 场景 / 判据 |
| 优先级建议 | P0/P1/P2 或 MUST/SHOULD/MAY（对齐 requirement-analysis 纪律） |

**转化三原则**（源自"需求→技术规范转化"通用方法论，在本 skill 的代际
方向上镜像适用）：

1. **细化澄清 ≠ 改需求**：遗留问题转需求的目的是把上一代模糊处**显式化**
   （模式示例：V(n) 某能力未明确硅前/硅后口径 → V(n+1) 显式化），不是借机
   扩 scope。
2. **多对多转化**：产品需求到技术规范"不是一对一的，是多对多的"——同理，
   一个遗留问题可裂解为多条需求（模式示例：某能力缺失 → 功能 + 性能（量化
   损耗上限）+ 里程碑三类需求），多条问题可合并为一条需求族（模式示例：
   某调测相关多项工作 → 一条调测能力需求族）。
3. **顺序交接**：项目管理上顺序做（需求 → 研发）；需求候选先进入需求文档
   基线，技术主导后与各领域多沟通不冲突——即需求侧锚点不被技术讨论静默改写。

### 2.5 衔接（Handoff）

1. **输出喂给 requirement-analysis skill**：候选清单作为其 Phase 1
   （Ingest & Normalize Inputs）输入基线的一部分，置于 `01_输入基线/`，
   内部件加 `_internal_` 前缀。
2. **CSV 纪律沿用**（定义见 requirement-analysis.md Project Conventions）：
   - **Source Tag**：`[T1-VERIFIED]`（上一代权威文档：风险登记册/gap 矩阵/
     正式纪要）、`[T2-CROSS-CHECKED]`（≥2 源互证）、`[UNVERIFIED]`
     （单源或推断——纯口述未落文档者至少 [UNVERIFIED]）。
   - **Mapping Type**：`[exact]` / `[approximate]` / `[composite]` /
     `[N/A]`（内部代际承接项无外部 spec 对应 → `[N/A]`）。
3. **编号纪律**：候选引用下一代需求编号前，先对用户提供的权威需求清单
   交叉核验（防**幽灵编号**——草稿号未入库不得当正式编号引用，见 §3）。
4. **与 gap-analysis 分流**：候选若需对外部规范对标深挖（spec vs 实现
   差距、竞品证据、F{N} 文档）→ 转 gap-analysis skill；本 skill 不做
   单 feature 深挖。

## §3 证据纪律与 QA 清单

### 3.1 证据纪律（HARD RULES）

1. **零编造**：严禁为满足 Q1 而编造"上一代已分析"（模式示例：某几份上一代
   文档若无 gap 分析就如实标"未做"，严禁补编）。
2. **来源链完整**：每条候选可回溯到用户材料锚（材料内行号/条目号/日志
   条目）；断链即 🔴（来源断裂；分级口径：✅一致/🔷轻修/🔶失配/🔴来源断裂）。
3. **不静默丢弃**：采集到的每条遗留问题，要么进候选，要么进 not-converted
   register（含三问未过原因）。
4. **双口径保留**：定级冲突不得以单一口径覆盖另一口径。
5. **幽灵编号防范**：草稿号（如未入库的编号段）引用前必须对用户提供的权威
   需求清单交叉核验；核验不过 → 标 `[UNVERIFIED]` + 待核。
6. **脱敏**：对外件沿用占位符约定（`MEMBER-XX-XXX`/`ORG-00`/`RVI-XXX`）；
   内部批评性评估与对外 roadmap 表述分件。

### 3.2 QA 清单

- [ ] 五源逐一盘点（用户未提供材料的源也显式记录"无材料"）
- [ ] 每条候选有来源链（材料内定位锚 + 材料内 ID）
- [ ] 每条候选有三问结论（Q1/Q2/Q3）
- [ ] 未转化项进 not-converted register（含理由）
- [ ] 双口径定级冲突项两口径并存
- [ ] Source Tag / Mapping Type 完备（沿用 requirement-analysis 定义）
- [ ] 引用的下一代需求编号经权威清单交叉核验（无幽灵号）
- [ ] 口述/反馈条目的工作日志锚符合 §1.1 口径（日期+条目/行号，无仓库路径）
- [ ] 内部件 `_internal_` 前缀；对外件无占位符泄漏

### 3.3 与 gap-analysis.md 轻量模式的关系

gap-analysis 管**规范差距**（外部 spec ↔ 内部 feature，需求编制期与修订期
均可触发）；本 skill 管**代际输入**（上一代遗留问题 → 下一代需求候选）。
一个需求候选可以同时触发两者：先用本 skill 生成候选（来源链指向 V(n)
风险/缺口），再用 gap-analysis 深挖该候选相对外部规范与竞品的差距
（F{N} doc）。前者答"这需求从哪来"，后者答"这需求做到什么程度才够"。

## §4 Worked Examples（模式级抽象示例）

> 以下示例为**模式级抽象**：不含任何真实产品编号、任务号、文档名或库内
> 路径；实际条目由用户材料提供。

### 4.1 模式一：能力口径缺（上一代未明确 → 下一代需求明确化）

- **遗留问题**（模式级）："某调测能力在上一代已有工作积累，但主要针对的
  场景是硅前；设计文档中又没有明确覆盖口径是硅前还是硅后。"
- **归一**：代际归属 = "V(n) 未明确"；闭环状态 = "口径缺（做了工作但文档
  未显式化）"。
- **三问预判**：Q1 通过（调测能力是交付能力，影响客户落地调试效率）；Q2
  通过（可表述为产品需求）；Q3 通过（可写场景口径：硅前/硅后分列）。
- **需求候选**：V(n+1) 明确提出该调测能力需求并细化（硅前/硅后显式化）。
- **转化原则应用**：原则 1（细化澄清）——把模糊口径显式化，而非扩 scope；
  原则 2（多对多）——上一代多个相关工件（如性能计数/断点/Trace 类手段）
  收敛为下一代一条需求族并细化。
- **来源链示例**：用户提供的某日工作日志第 N 条逐字口述（§1.1 口径）→
  归一条目 → 候选来源链。

### 4.2 模式二：交付文档体系差距（差距矩阵 → 需求侧锚点）

- **遗留问题**（模式级）：上一代交付文档体系在若干部分存在差距（如设计
  对应性未核实/用户手册条目缺位/集成文档缺位/验证报告维度缺位/配套软件栈
  未纳入），五列矩阵逐行带材料内来源锚。
- **归一**：每行 Gap 的代际归属 = "V(n) 缺失/未纳入"；闭环状态 = "未闭环
  （刷新未开始/进行中）"。
- **锚点衔接**：Gap 处置列直接引用下一代需求文档章节锚——"需求侧锚点"列
  即来源链的镜像（gap → 需求反向映射）。
- **幽灵编号教训**：下一代需求编号若为草稿号，引用前须对权威需求清单交叉
  核验。
- **双口径**：内部底稿（批评性 gap 评估）与对外件（短板转 roadmap 表述）
  分件，内部件不外发。

## §5 References（由用户提供）

本 skill **不内置库内锚**。调用时由用户提供以下类型的材料及其材料内定位锚
（行号 / 条目号 / 章节锚 / 纪要条目 / 日志条目，口径见 §1.1）：

| 素材类型 | 用户提供的材料 | 支撑环节 |
|---------|---------------|---------|
| 产品风险登记册 | 风险条目 + 定级口径 + 条目 ID/行号锚 | §1 源 1 / §2.1-2.2 |
| Gap 矩阵 | 五列结构（或等效）+ 行级来源锚 | §1 源 2+5 / §2.2 / §4.2 |
