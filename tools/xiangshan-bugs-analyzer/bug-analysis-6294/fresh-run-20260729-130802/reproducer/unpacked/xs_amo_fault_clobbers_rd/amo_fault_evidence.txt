=== XS bug: a store-page-faulting AMO clobbers its destination register (rd) ===
reproducer: repro_amo_fault_clobber.elf  (deterministic; reproduces on BOTH
  kunminghu-v3 d97789de12 AND 2b5769e8b2 -> not tip-specific)

--- faulting sequence (fuzz body) ---
  la    x9, d_1_0          # x9 = &d_1_0
  addi  x9, x9, -24        # x9 = 0x20008  (an address with no store permission)
  amoxor.w x9, x13, (x9)   # atomic to 0x20008 -> STORE PAGE FAULT (scause=0x0f)

--- the trap (agreed by both models) ---
  scause=0x0f (store/AMO page fault)  sepc=0x2b5c  stval=0x20008

--- the divergence: x9 (rd of the faulting AMO) after the trap ---
  NEMU (reference): x9 = 0x0000000000020008   (rd PRESERVED - correct)
  XS   (DUT):       x9 = 0x0000000000000000   (rd CLOBBERED to 0 - WRONG)
  Surfaces via the trap handler's register save/reload: XS's saved slot holds 0
  (difftest first flags s1/x9 at the reload pc 0xffffffffffe02370).

=== WHY XS IS WRONG (RISC-V unpriv spec, precise traps) ===
  An instruction that takes a (precise) trap must NOT modify architectural
  registers - rd must be unchanged so the instruction is restartable. amoxor.w
  that store-page-faults must leave x9 = its input address 0x20008 (as NEMU does).
  XS writes x9 = 0, so a trap handler that maps the page and re-executes has lost
  the AMO's address operand -> silent wrong execution on resume.

  Deciding signal (Core Rule): the committed ARCHITECTURAL integer register x9,
  which difftest compares each commit -> XS=0 vs NEMU=0x20008 right after the AMO.
  RTL waveform (VerilatedVcd, ~101MB, window around cycle 12087) captured for
  maintainer inspection (too large to attach; available on request).
